Design points worth knowing
- `checkout_place_with_bundles` passes no coupon to `checkout_place`, so `checkout_place_full` calls `checkout_place` directly for carts without bundles (coupon path unchanged) and the bundle wrapper only when a bundle is present (bundle + coupon raises `KH:BUNDLE_COUPON_EXCLUDED`, nothing is silently removed).
- Razorpay: `payment_prepare` and `payment_attach` still read `orders.total_paise` inside the database. `checkout_place_full` finishes updating that column before it returns, so nothing about the payment path changed.
- Shipping used to be trusted from the caller (`order_create`). `checkout_place_full` now raises `KH:PRICE_CHANGED` when it differs from `shipping_expected`.

Not changed: coupons rules, GST on invoices, Razorpay code, webhook code, UI, API routes.

## Stage 7D: wishlists (v9 tree). NOT RUN beyond a syntax parse and 4 helper tests under the temporary shim
The database side already existed and was already tested in `bundles_wishlists_selftest.sql` (`wishlist_add/remove/list/merge/track_to_cart`, 100-item cap, unique per member and product, no member id in the events log). It had no application code. Added:
- `api/cart/[action].ts`: actions `wishlist` (GET), `wishlist-add`, `wishlist-remove`, `wishlist-to-cart` (POST). They sit in the cart function because the project already has 12 serverless functions (the Hobby limit); no new function file. They inherit the cart handler's rules: the cart preview flag, per-IP rate limits, origin plus CSRF header on writes, signed-in member from the session cookie re-checked against `members`. The browser sends a product slug only; the member id is never taken from the request, so one customer cannot read or change another's list.
- `server/wishlist.ts` (slug to id, rpc wrappers), `shared/wishlist.ts` (+ test: row mapping, no ids exposed, no price for unavailable products), `shared/inventory.ts` (`WISHLIST_FULL` message).
- Add to bag from the wishlist: only when exactly one pack size is orderable; with several sizes the API answers `choose_size` and the page sends the customer to the product page. Adds one unit (capped), reuses `setSavedItem`, records the `to_cart` event, returns the re-priced bag.
- UI (existing classes and tokens only): `/wishlist` page (loading, error with retry, empty, signed-out, unavailable and out-of-stock states, price and availability read fresh from the database), `WishlistButton` on the product page under Add to bag, a Wishlist link in the account menu. `/wishlist` is in `shared/private-routes.json` (noindex). A few lines of CSS appended to `src/styles/bag.css`.
Decisions and limits
- No guest wishlist exists in the code, so nothing was migrated; signed-out visitors are sent to sign in. `mergeWishlists` in `shared/bundles.ts` and `wishlist_merge` remain unused.
- Product cards were left untouched (the save control is on the product page and the wishlist page only).
- The wishlist works only where the bag is open (same flag as the cart). The header does not show a count; the page does.
- Not tested: the API actions (no mocked API test written), the pages in a browser, any concurrency.
